# АвтоКлик · План работ по ролям

> Кто что делает при реализации приложения, в каком порядке и с какими зависимостями. Технические обоснования — в `03-техническая-документация.md`, сроки и оценки — в `02-план-задач.md`.

## Состав ролей

Стек из техдокументации (Python/FastAPI, отдельный сервис-коллектор, Postgres + Redis + OpenSearch, CatBoost и survival-модели, Flutter, Kubernetes) требует восьми ролей. Меньше — только за счёт совмещения, и ниже сказано, какие совмещения безопасны.

| Роль | Зона ответственности | Что ломается, если роли нет |
|---|---|---|
| **Backend-ядро** | Модульный монолит API: домен, БД, миграции, платежи, отчёты, права | Всё |
| **Сбор данных** | Сервис `Collector`: адаптеры источников, расписание, кэш, деградация, рубильники | Продукт нечего показывать |
| **ML и расчёты** | Оценка цены, дедупликация, модель отказов и расчёт ремонта, скоринг перекупа | Три из пяти дифференциаторов |
| **Мобильный клиент** | Flutter-приложение, офлайн-кэш, пуши, SSE-прогресс проверки | Продукта нет у пользователя |
| **Дизайн** | Дизайн-система, 53 компонента, состояния, доступность | Разработка рисует сама, и результат расходится с концепцией |
| **DevOps** | Окружения, CI/CD, наблюдаемость, сетевая изоляция коллектора | Нельзя выкатываться и нельзя понять, что сломалось |
| **QA** | Пирамида тестов, контрактные тесты парсеров, канарейки источников | Поломку парсера узнаём от пользователей через сутки |
| **Аналитика и контент** | Справочники, приёмка болячек, метрики, калибровка | C2 и C3 пустые, решения принимаются на ощупь |

**Безопасные совмещения на старте:** DevOps + Backend-ядро (до первого продакшена), Аналитика + QA (до R2). **Несовмещаемо:** ML и Сбор данных — это разные режимы работы, и совмещение приводит к тому, что не делается ни то, ни другое. ML — критический путь: дедупликация и оценка цены блокируют пять экранов.

## Порядок работ

### Этап 0 · Каркас (блокирует всех)

| Роль | Задача |
|---|---|
| Backend-ядро | Структура репозитория, конфигурация, подключение БД, миграции, health-check |
| DevOps | CI: линт, типы, тесты на каждый коммит; контейнеры; окружение stage |
| Дизайн | Токены в код, включая исправления контраста из `04-дизайн-система.md` |

Пока этап 0 не закрыт, остальные роли работают в своих каталогах на фикстурах, без общей БД.

### Этап 1 · Параллельные вертикали

Четыре независимых направления, у каждого свой каталог и свои тесты. Пересечение только через доменные типы из этапа 0.

| Направление | Роль | Каталог | Содержание |
|---|---|---|---|
| Сопоставление | ML | `avtoklik/matching/` | Нормализация госномера и VIN, каскад дедупликации, выбор канонической цены |
| Знания о моделях | ML | `avtoklik/knowledge/` | Модель отказов по пробегу, расчёт ожидаемых затрат, стоимость из деталей и нормо-часов |
| Сбор | Сбор данных | `avtoklik/collector/` | Контракт адаптера, извлечение фактов из текста, оркестрация опроса с деградацией |
| API | Backend-ядро | `avtoklik/api/` | Эндпоинты флоу B, контракт SSE-прогресса проверки |

### Этап 2 · Сборка вертикали «проверка»

Соединение в сквозной сценарий B1 → B2 → B3. Первый момент, когда продукт делает то, что обещает. Ведёт Backend-ядро, участвуют все.

### Этап 3 · Клиент и остальные флоу

Мобильный клиент на замороженных контрактах API, далее C, D, E по плану релизов.

## Что сделано в этой сессии

Реализованы те части, которые не зависят от внешних договорённостей и проверяются тестами прямо сейчас:

| Модуль | Что внутри | Роль |
|---|---|---|
| Каркас проекта | `pyproject.toml`, конфигурация, линт, типы, тесты, CI | Backend-ядро, DevOps |
| `avtoklik/knowledge/` | Модель отказов по пробегу и расчёт ожидаемых затрат на ремонт — то, что заказчик выделил отдельно | ML |
| `avtoklik/matching/` | Нормализация госномера и VIN, каскад дедупликации | ML |
| `avtoklik/collector/` | Контракт адаптера источника, оркестрация с деградацией, извлечение пробега и стоимости из текста | Сбор данных |
| `avtoklik/api/` | Эндпоинты проверки и контракт SSE-прогресса | Backend-ядро |

**Чего сознательно нет.** Живых парсеров Авито, Авто.ру, Дрома и форумов. Адаптеры написаны как контракт и протестированы на фикстурах, но ни один не ходит на реальную площадку. Причина в `01-концепция.md` §6: правовой статус такого сбора — открытый вопрос Б2 и Д8, и до ответа юриста писать боевой парсер значит закладывать в продукт риск, который мы сами же пометили как критический. Как только доступ определён, адаптер пишется под готовый контракт за день.

Каталоги остальных ролей (`mobile/`, `infra/`) появятся, когда до них дойдёт очередь по этапам выше.
